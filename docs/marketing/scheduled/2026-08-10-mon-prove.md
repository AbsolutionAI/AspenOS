# Mon Aug 10 — Prove before ship: the eval gate that saved us $400

## Draft post

We nearly shipped a broken agent and didn't catch it until the eval gate caught it. Here's what happened:

One of our Paperclip agents — the one that scans repo changes and drafts Linear tickets — started writing tickets that were technically correct but completely useless. It would describe the code change accurately, but its priority assignment was broken: everything was P2. Critical security fix? P2. README typo? P2. Broken CI pipeline? P2.

A human reviewer would catch that, eventually. But "eventually" in a multi-agent fleet means the broken pattern propagates — downstream agents start scheduling P2 fixes ahead of real P1 work, and suddenly your triage queue is a shuffled deck.

The fix wasn't more human review. It was a **commitment eval** — a small assertion that runs before the agent's output reaches the next node in the pipeline:

> **"Is the priority signal present and non-uniform?"**

If every ticket in the batch is P2 with no variance, the gate halts the output and flags the agent for retrain. That one assertion saved us roughly $400 in downstream waste (mis-triaged issues, context resets, re-runs) in the first week.

Three lessons:
1. Tests for agents are cheaper than tests on agents — gate the output, don't rebuild the model.
2. The simplest assertion is often the most impactful: "is there variance in the signal?"
3. If your pipeline has no eval gate between agent output and agent consumption, you're running on trust. Code gets a CI gate before merge. Agents should too.
