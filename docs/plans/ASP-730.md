# ASP-730 — Run the full Python suite (`tests/`) in CI

## Problem

`.github/workflows/ci.yml` never runs `tests/` wholesale. It runs two *named* test files
(`test_package_signatures.py`, `test_model_digests.py`) plus `scripts/smoke-test.sh`.
A red full Python suite is therefore invisible to CI and surfaces only in nightly §13
and in Aider preflight, where a non-zero exit has repeatedly been misread as a regression
in the change under review. `docs/ops/NIGHTLY_PACKAGING_DEPLOY_CHECK.md` records this as an
open gap, exposed by the ASP-706 incident (`tests/test_holographic_ingest.py` failing on any
host without `ruamel` while CI stayed green).

Closing that gap immediately exposes the second half of the problem: **the suite has never
been executed on the interpreter CI uses.**

## Discovery: the baseline is red on 3.12, and it is a real bug

`services/hitl.py` guards its optional `aiohttp` import:

```python
try:
    from aiohttp import web
except ImportError:
    web = None
```

but then annotates module-level functions with `web.Response`:

```python
def _json_response(data: dict, status: int = 200) -> web.Response:
```

Without `from __future__ import annotations`, PEP 526 evaluates that annotation at
function-definition time, so the module cannot be imported at all when `aiohttp` is absent:

```
File "services/hitl.py", line 963, in <module>
    def _json_response(data: dict, status: int = 200) -> web.Response:
AttributeError: 'NoneType' object has no attribute 'Response'
```

Measured on a clean 3.12 venv with only `pytest pytest-asyncio pyyaml` installed:

```
12 failed, 454 passed, 4 skipped
```

Every one of the 12 is the same root cause — `src/python/gatekeeper/vault_gate.py` loads
`services/hitl.py` lazily, fails, and `_resolve_hitl_paths()` propagates. The gatekeeper
vault-gate tests (`test_gatekeeper_vault_gate.py`, `test_gatekeeper_dual_human.py`) audit
`vault_unavailable` and then `KeyError: 'vault_approval_id'`.

This stayed hidden for three independent reasons, all of which this ticket removes:

| Environment | Why it was green |
|---|---|
| CI | never ran `tests/` |
| nightly §13 (`nightly.yml`) | installs `aiohttp`, so the import succeeds |
| local nightly host | Python **3.14**, where PEP 649 defers annotation evaluation by default |

So `services/hitl.py` is unimportable on *any* Python < 3.14 host without `aiohttp` —
which is every `ubuntu-latest` runner this repo builds on. The optional import guard the
file already has is silently defeated by its own annotations.

Six sibling service modules carry the identical latent landmine
(`services/audit.py`, `webhooks.py`, `planner.py`, `evaluator.py`, `kill_switch.py`,
`handoff.py`); only `hitl.py` is reached by the suite today. Fixing one and leaving six
re-creates the exact drift this ticket exists to close, and the fix is one line each.

## Change

1. **`.github/workflows/ci.yml`** — new `python-test-suite` job, **required** (no
   `continue-on-error`, no `if: always()` soft gate):
   - `actions/setup-python@v5` at `3.12`, matching `nightly.yml` and the other Python jobs.
   - `pip install pytest pytest-asyncio pyyaml` — the deps the suite actually requires.
   - `python -m pytest tests/ -v --tb=short -rs` — the repo's established invocation shape
     (`check-nightly.sh` §13 uses the same flags), plus `-rs` so the four optional-dependency
     skips print their reasons in the log instead of being invisible.
   - `timeout-minutes: 15`.

   The four optional deps (`aiohttp`, `mcp.server`, `nats-py`, the out-of-repo Hermes
   holographic plugin / `ruamel`) are deliberately **not** installed, so the four documented
   skips keep skipping and the new gate's baseline matches what Aider preflight sees.

2. **`from __future__ import annotations`** on the seven guarded service modules. This is
   the fix the guard was always asking for: deferring annotation evaluation is what makes
   `web = None` survivable at import time. Verified safe — no `typing.get_type_hints` /
   `__annotations__` introspection anywhere in `services/`, `src/`, `agents/`,
   `dashboard/`, or `tests/`, and no pydantic models in these files, so string annotations
   are never resolved at runtime. Plain `@dataclass` in `hitl.py` is unaffected.

   With the future import, the seven quoted self-referential annotations those files carry
   become redundant, so their quotes are dropped too — **net zero new ruff findings**
   (verified by per-rule before/after comparison: 106 findings before, 106 after).

3. **`tests/test_ci_assertions.py`** — a contract test in the existing style, asserting
   `ci.yml` runs `tests/` wholesale, that the job is not a soft gate, that it matches the
   nightly interpreter and installs no optional dep, and that every guarded-optional-import
   service module carries the future import. Without it, the next sweep can silently drop
   the job or reintroduce the landmine; this file already exists to pin exactly that class
   of drift.

4. **`docs/ops/NIGHTLY_PACKAGING_DEPLOY_CHECK.md`** — "Known deviations" drops the
   open-gap note, and keeps the ASP-706 `ImportError`-guard history (that is still the
   reason the holographic skip is safe).

## Discovery #2 — the gate immediately found a host-specific test

The first CI run of the new job failed on a second, independent environment-only defect:

```
tests/test_paperclip_memory_ingest.py::TestPaperclipMemoryCLI::test_cli_no_ingest_dir_uses_default
assert rc == 0
E   assert 2 == 0
paperclip-memory: ingest skipped: [Errno 13] Permission denied: '/home/tech'
1 failed, 469 passed, 4 skipped
```

`scripts/memory_ingest.py` defaults `DEFAULT_INGEST_DIR` to this repo's host convention
`/home/tech/.aspen/memory/ingest`. The test deliberately exercised the real default, so it
was host-specific *and* wrote a real ingest record into the operator's live memory dir as a
side effect. `ingest_paperclip_record` imports `DEFAULT_INGEST_DIR` at call time and always
passes it explicitly, so the test now redirects the module attribute at `tmp_path`. The
resolution path under test is unchanged and the assertion got *stronger*: `is not None`
became an exact match on the resolved default plus proof the directory was created.

The hardcoded host paths in `scripts/memory_ingest.py`, `scripts/memory_promote.py`,
`scripts/holographic_ingest.py` and the install scripts are left alone on purpose — they are
the repo-wide deployment convention (`/opt/agnetic/`), so changing the production default is
a separate decision with a real blast radius, not something to bundle into a CI ticket.

## Not doing

- **Not** installing `aiohttp` / `mcp` / `nats-py` in the new job. That would delete two of
  the four documented skips and turn this ticket into "make the suite green on 3.12 with
  every optional dep", a materially bigger baseline change that deserves its own ticket
  and its own review.
- **Not** adding `--tb=no` / `xfail` / skip guards to any of the failures. Both were real
  bugs in guards the code already had; the fixes are the one line each guard implies, not a
  suppression. No test was deleted or skipped to make the gate green.
- **Not** de-hardcoding `/home/tech` in `scripts/memory_ingest.py`,
  `scripts/memory_promote.py`, `scripts/holographic_ingest.py`, or the install scripts.
  Those are the repo-wide deployment convention (`/opt/agnetic/`), so the production default
  is an Architect call, not a CI-ticket side effect. Worth its own ticket.

## Escalated, not fixed here: `master` has no branch protection at all

Verified against the API while landing this:

```
GET /repos/AbsolutionAI/AspenOS/branches/master/protection
  -> 404 {"message": "Branch not protected"}

GET /repos/AbsolutionAI/AspenOS/rulesets
  -> []
```

So there is no required-checks list to add `python-test-suite` to — nothing on `master` is
required. The new job *reports* red on a red `tests/` (proved, run `37190783476`), but
nothing blocks a merge. "Required" in this change means *the job has no soft-gate escape
hatch*, not *the merge is gated*.

That is a governance gap rather than a code gap, and it is a strictly larger decision than
this ticket, so it is raised as its own follow-up rather than configured unilaterally here.
Until it lands, treat "red in CI" as advisory on this repo — which is exactly the posture
that let ASP-706 through in the first place.
