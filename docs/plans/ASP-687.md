## Problem

ASP-379 built `ToolAnomalyDetector` (`src/python/sentinel/tool_anomaly.py`) as a
**pure library + offline CLI**. `docs/solutions/asp-379-tool-anomaly.md` closes with
the explicit deferral:

> - [ ] Live consumption hook-up (JetStream consumer → detector → findings journal/table)
>   — deferred; a follow-up issue tracks the wiring.

That follow-up is this ticket. Today **nothing in the running system ever calls
`feed()`**. The detector has exactly one caller: a human or cron running
`scripts/tool-anomaly.py scan` over a JSONL file, after the fact. A burst that
happens at 03:00 is discovered whenever somebody remembers to look.

## Discovery finding — the wiring is not the only defect, and the defect is worse than the gap

Before designing the consumer I probed the detector's **streaming** semantics,
because streaming is the whole point of this ticket and the batch CLI never
exercises it. R2/R3/R4 fire at exact threshold crossing (`== min`) and therefore
emit once per burst. **R1 does not.** It is a *set-state predicate* — "does the
window contain a sensitive read followed by an egress" — evaluated over the whole
retained history on every single arrival:

```
event 0  tool.read_file /etc/shadow            -> 0 findings
event 1  tool.http_post  https://evil/x         -> 1  sensitive_read_then_egress
event 2  tool.search_files docs/readme.md       -> 1  sensitive_read_then_egress   <- same incident
event 3  tool.search_files docs/readme.md       -> 1  sensitive_read_then_egress   <- same incident
...                                             (identical rule/actor/message every time)

scan() batch, 12 events -> 11 findings, R1 = 11
distinct (rule, actor, message) among those 11: 1
```

So **one exfiltration incident emits one finding per subsequent audit event from
that actor inside the 120s window.** This is not only a wiring problem:

- It already corrupts the shipped CLI: `scripts/tool-anomaly.py scan` over a real
  day's journal reports the same incident dozens of times, and the count scales
  with how busy the actor is — an attacker who stays active is amplified hardest.
- Wiring it to a paging subject without fixing it converts a **detector into a
  paging amplifier**. R1 (high) is precisely the rule the threat model says ops
  should *page* on (§8.7: "so ops can page on R1 (high)"). One incident, hundreds
  of pages, and the first page gets muted — which is the outcome the fail-open
  design was built to avoid.
- The stated emit-once contract in `docs/solutions/asp-379-tool-anomaly.md`
  ("Emit-once per burst … so no spam as the window slides") is **only true for
  R2–R4**, and H-015/F-015 are marked Closed on the strength of "12 hermetic
  tests" — none of which append a trailing event after the pair.

Fixing this is a precondition for the wiring, not a side quest. Same defect class
as ASP-684's TLS knob that read as enabled but was ignored on `edge`: a security
control that reports the wrong thing is worse than a missing one.

## Design decisions

| # | Decision | Alternative rejected | Why |
|---|----------|---------------------|-----|
| 1 | Fix R1 emit-once in the **detector**, not with a cooldown in the consumer | consumer-side dedupe/suppression | The bug is in the detector's own contract and already reaches users through the shipped CLI. Suppressing in the consumer leaves `scripts/tool-anomaly.py` wrong and the fix invisible to anyone who later wires the detector up again. |
| 2 | R1 fires only when the **just-arrived** event is the egress that completes the pair; the emitted finding is deduped on a stable correlation key `(actor, read_ts, egress_ts)` | dedupe alone; predicate-only change | Predicate-only still double-fires on out-of-order/late delivery (the arriving event may not be the ts-newest). Keying on arrival matches `_rule_bursts`, which already evaluates the just-arrived `history[-1]`, and the key closes the redelivery case too. |
| 3 | Also dedupe **`event_id`** in detector history | leave as-is | A JetStream consumer is at-least-once by default. Without it a redelivered audit event is counted twice and inflates R2/R3 counts — a **false-positive** burst from a single real tool call. 4 lines, and it is the difference between a detector that survives the move to a durable consumer and one that manufactures incidents. |
| 4 | **Core NATS push subscribe**, not a durable JetStream pull consumer | `js.pull_subscribe(durable=…)` | Matches the established sentinel pattern (`AuditEventConsumer`, `FleetOverviewProducer` both use `nc.subscribe`). At-most-once, so no redelivery gap *and* no ack-storm failure mode. Durable delivery is recorded as a follow-up rather than assumed — it needs a live broker to verify and this repo has no CI broker. |
| 5 | Subject `aspen.sentinel.tools.anomaly`; **no ACL change** | edit `nats/fleet-accounts.conf.tmpl` | `aspen.sentinel.>` is already allowed for STARSHIP_OPS publish+subscribe and imported by STARSHIP_EDGE. Verified, not assumed — see Verification. New subject needs `nats/subjects.yaml` registration only. |
| 6 | Findings written to their **own** fsync'd JSONL journal + best-effort JetStream | publish-only | Same write topology as `AuditEventPublisher` / `FleetOverviewProducer`: durable offline, live when online. Without a journal, "offline" silently means "findings vanish". |
| 7 | **No new nightly section** | add Section 23 | Section 23 is claimed by the in-flight ASP-701 branch (NATS TLS, blocked on Auditor ASP-703). Both adding a section 23 guarantees a merge conflict on `scripts/check-nightly.sh` plus check-count drift in the runbook. New tests are already gated by existing Section 13 (whole-suite pytest). Flagged to Aspen Architect instead — see Open questions. |

## Out of scope

- Blocking / deny path for findings. The detector stays fail-open and log-only; that
  was a deliberate ASP-379 decision and this ticket does not reopen it.
- Alert routing (PagerDuty/Buzz), dashboards for findings, retention tuning.
- Durable JetStream pull consumer (decision 4) — follow-up.
- New nightly section (decision 7).

## Verification

  (no regression in the sentinel package)
- full `pytest tests/ -q` — required because `feed()` semantics changed and
  `ToolAnomalyDetector` is the only thing standing between a burst and a page
- `bash -n` equivalent for the new CLI + subprocess CLI round-trip (`scan`/`tail`/`check`)
- R1 emit-once proven by **mutation**: break the dedupe key, confirm the test goes red,
  restore. A test that cannot fail proves nothing.
- ACL claim verified by grep against the template, recorded in the handoff comment —
  not asserted by a test that could pass vacuously.
