# ASP-369 — Plan: Revisit plant-edge→plant-alpha ACL (pivot risk)

**Issue:** ASP-369 (HIGH, F-022 / H-021)
**Parent:** ASP-298 — Security Threat Model v2.2
**Status:** Implemented
**Date:** 2026-09-20

## 1. Problem

`config/fleet.yaml` ships a bidirectional cross-plant ACL:

```yaml
acl:
  default: same_plant_only
  allow:
    plant-alpha: [plant-edge]
    plant-edge: [plant-alpha]
```

`plant-edge: [plant-alpha]` gives edge nodes an allow-list path to reach the
ops plant. If an edge node is compromised it can pivot into `plant-alpha`
through this edge. The v2.2 threat model (ASP-298) zone table already treats
edge as a limited subject set ("Z3 → Z1 heartbeat + proxy only … no
mission/write subjects"), so the ACL edge contradicts the zone boundary
(F-022).

## 2. Decision (recorded)

**Remove `edge → alpha`; keep `alpha → edge` (ops-initiated).**

- Least privilege: edge nodes never initiate cross-plant traffic into ops.
- `alpha → edge` stays so ops can still manage/reach edge nodes — operator
  (ops-plant) initiated only, i.e. brokered via ops-side subjects.
- `plant-range` remains isolated with an explicit empty allow list.
- Direction semantics: source plant initiates to target plant; removing the
  edge entry makes any edge-initiated cross-plant request fail-closed via the
  `same_plant_only` default in `fleet_policy.check_cross_plant`.
