# ASP-376: F-012 — cgroups per-agent resource limits

**Status:** IMPLEMENTATION
**SEV:** MEDIUM
**Hazard:** H-012 (resource exhaustion)
**Parent:** ASP-298 (threat model refresh — *resource exhaustion / noisy neighbor* row)

## Objective

Bound CPU, memory, and PID ("tasks") usage of every Starship OS service unit on
cgroup v2 systems via systemd *drop-in* snippets committed to git — never
applied live to `bt-asp-srv`. Deliver the snippets, wire them into packaging so
they ship on install, document the knobs, and prove existence with tests.

## Why drop-ins, not unit-file edits

Unit files in `systemd/*.service` are the opaque baseline; operators may pin
their own overrides. Shipping cgroup limits as `<unit>.service.d/10-cgroup-limits.conf`
keeps the limits an explicit, overrideable layer:
- systemd (cgroup v2, unit(5)) loads `*.d/*.conf` drop-in dirs "type 2"
  adjacent to the unit file in the search path, so drop-ins staged at
  `lib/systemd/system/<unit>.service.d/` merge into the shipped unit with no
  postinst/apparmor-style hooks.
- `install-systemd.sh` (dev/VM path) copies the same drop-ins into
  `/etc/systemd/system/<unit>.service.d/`, which always wins over the shipped
  unit — correct precedence for override-ability.

## cgroup v2 knobs used

| Knob | cgroup controller | Meaning |
|------|-------------------|---------|
| `MemoryMax=` | memory | hard OOM ceiling (absolute bytes / suffix) |
| `MemoryHigh=` | memory | soft throttle ceiling (memory pressure before OOM) |
| `CPUQuota=` | cpu | absolute CPU cap across the cgroup's cores (`100%` = 1 core) |
| `TasksMax=` | pids | hard cap on tasks (threads/processes) in the cgroup |
| `…Accounting=yes` | cpu/memory/tasks | explicit accounting (systemd defaults on when limits set; kept explicit) |

Live verification recipe (documented in ops doc; NOT run on bt-asp-srv):
`systemctl show <unit> -p MemoryMax,MemoryHigh,CPUQuotaSec,TasksMax` and
`systemd-analyze cat-config systemd/system/<unit>.service.d 2>/dev/null | grep -E "MemoryMax|MemoryHigh|CPUQuota|TasksMax"`.

## Per-unit limits

| Unit (`systemd/<name>.service`) | Role | CPUQuota | CPUWeight | MemoryHigh | MemoryMax | TasksMax | IO |
|---------------------------------|------|----------|-----------|-----------|-----------|----------|----|
| `agnetic-agent@` (per-agent template) | agent daemon per `%i` (proxy/romi/ergo) | 50% | 100 | 384M | 512M | 128 | yes |
| `agnetic-message-history` | message persistence | 50% | 100 | 384M | 512M | 128 | yes |
| `agnetic-nats` | NATS bus | 100% | 200 | 192M | 256M | 256 | yes |
| `agnetic-dashboard` | web dashboard | 25% | 50 | 192M | 256M | 128 | no |
| `agnetic-staragent` | guard binary | 25% | 50 | 96M | 128M | 64 | no |
| `agnetic-status-bridge` | tray/status bridge | 25% | 50 | 96M | 128M | 64 | no |
| `starship-fleet` | fleet manager | 50% | 100 | 384M | 512M | 128 | yes |
| `starship-health-checker` | health probe | 25% | 25 | 96M | 128M | 32 | no |

Rationale: the box runs local Ollama/llama-server outside these units. The
agent template and fleet manager share the same Python-daemon profile (50% /
512M); NATS (the bus backbone) gets a full core with the highest CPU weight;
lightweight bridges get a quarter core. Practical NOOP: profiles were tuned
down from the initial draft (agent 150%→50%) after load review so agent units
cannot starve the host's local LLM workers. An N-cap in TasksMax directly
bounds the pids-controller threat (fork bombs / leaked threads) that
`max_connections` does for NATS.

## Non-goals

- No live `systemctl` / cgroup application on `bt-asp-srv` (all board-committed
  config ships in git).
- No per-instance differentiation of `agnetic-agent@` (template covers all `%i`).
- No MemorySwapMax/Low/DeviceAllow — out of scope for resource limits ticket.
- No changes to base unit files or AppArmor profiles.

## Acceptance criteria

1. For each of the 8 units, `systemd/<unit>.service.d/10-cgroup-limits.conf`
   exists, has a `[Service]` section, and sets `MemoryMax`, `MemoryHigh`,
   `CPUQuota`, `TasksMax`, plus explicit accounting.
2. All unit `CPUQuota` values ∈ {25%, 50%, 100%} (tuned down from the draft
    {25%, 50%, 100%, 150%} during implementation); `TasksMax` ≥ 32;
   `MemoryHigh` < `MemoryMax`.
3. `build-deb.sh` copies `.service.d/` dirs into `lib/systemd/system/` and
   validates at least the agent drop-in in the payload layout.
4. `install-systemd.sh` installs drop-ins to `/etc/systemd/system/<svc>.service.d/`.
5. `tests/test_cgroup_limits.py` passes (fixture, no live systemd).
6. `scripts/check-nightly.sh` Section 20 all green; overall baseline updated.
7. `docs/ops/CGROUPS_RESOURCE_LIMITS.md` documents knobs + per-unit table.
8. Compound note `docs/solutions/asp-376-cgroups.md` committed.
