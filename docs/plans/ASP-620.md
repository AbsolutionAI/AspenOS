# Plan: ASP-620 — Implement plugin update() — local-path update

## Problem

`services/plugin_manager.py:619-628` implements `PluginManager.update(name)` as a
placeholder that always prints "Marketplace update not yet implemented." and
returns `False`. Meanwhile `install_from_path` refuses to install a plugin that
already exists (`services/plugin_manager.py:605-607`: "already installed. Use
update instead.") — so an installed plugin can never be replaced. That is a
dead-end for anyone with a newer plugin tarball/directory.

## Solution

Implement a local-path update that mirrors the existing offline/local-first
install model used by `install_from_path`:

- `update(name, source=None, force=False) -> bool`
  - `source=None` keeps the existing marketplace behavior (documented stub: print
    marketplace message, return `False`) — no backend exists to fetch from.
  - `source=<path>` performs a local-path update:
    1. Validate `source` is a directory containing `plugin.yaml`.
    2. Parse the new manifest; require `new_manifest.name == name`.
    3. Refuse downgrades (`new < installed`) and same-version no-ops unless
       `force=True`.
    4. Copy `source` to a temp sibling dir, run python deps install + setup hook
       against the temp copy **before** the swap.
    5. Atomically swap: rename existing plugin dir to `.bak`, temp to the plugin
       dir, rollback to `.bak` on failure, remove `.bak` on success.
    6. `self.discover()` + `_persist_enabled_state()` so version/state are fresh.
    7. Print updated version and return `True`.
- Wire `update` into the CLI (`cmd_update`, `commands` map, `cmd_help`) and keep
  `plugin_manager.py update <name> <path>` semantics.
- Update `docs/PLUGIN_GUIDE.md` method table row for `update`.

Version comparison reuses the tuple-comparison helper pattern already present in
`_check_version_compat`.
