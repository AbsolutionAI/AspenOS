# Plan: ASP-375 — H-011/F-011 NATS rate limiting + tighter connection limits

## Problem

Security threat model (ASP-298 refresh) DoS row — *Flood fleet subjects* — mitigates
with `max_connections` + `max_payload` only. Current NATS server configs are
minimal:

- `nats/agent-bus.conf` — `max_connections: 100`, `max_payload: 8MB`, nothing else.
- `nats/fleet-bus.conf` — `max_connections: 256`, `max_payload: 8MB`,
  `authorization { timeout: 5.0 }`, nothing else.
- `nats/fleet-accounts.conf.tmpl` — same minimal global block, no per-account
  connection/subscription caps.

A compromised or malicious bus client can therefore: hold many auth handshakes
open, ignore slow-consumer pings, open unbounded subscriptions per connection,
amortize large pending buffers, and let closed-connection tracking state grow
without bound. Auth-handshake exhaustion has no cap in fleet-bus (timeout 5.0s
vs the 2s default).

This ticket (F-011) goes beyond the existing `max_connections`: apply server-wide
rate/connection limits and auth-failure hardening to the fleet bus and accounts
configs, and bound per-account blast radius. Validated against the pinned
nats-server v2.14.x (ISO installs 2.14.3; local toolchain 2.14.5).

## Approach

Verified against nats-server v2.14.5 source (`server/opts.go`):
`auth_failure_timeout` / `auth_timeout` are **not** config fields in this
version, so "auth failure rate limiting" is delivered through the native knobs
that bound auth-handshake resource use and failed-connection bookkeeping:

1. **Global hardening block** (added to `agent-bus.conf`, `fleet-bus.conf`,
   `fleet-accounts.conf.tmpl`):
   - `max_pending: 16MB` — per-connection buffered-bytes cap (default 64MB;
     must stay >= `max_payload` 8MB).
   - `max_control_line: 4KB` — cap oversized CONNECT/PUB control lines.
   - `max_subscriptions: 512` — cap subscription floods per client (default: unlimited).
   - `max_closed_clients: 4096` — cap retained closed-connection state (default 10000).
   - `max_traced_msg_len: 512` — cap debug/trace log amplification.
   - `write_deadline: 5s` — cap write stalls (default 10s).
   - `ping_interval: 30s`, `ping_max: 3` — faster slow-consumer detection
     (defaults 2m/2).
   - `connect_error_reports: 3600`, `reconnect_error_reports: 4` — explicit,
     documented error-report throttling for connect/auth-failure floods.
2. **Auth-failure hardening** in `fleet-bus.conf`: lower
   `authorization { timeout: 2.0 }` (5.0 → default 2s) so a handshake that does
   not complete auth in time is dropped. Accounts mode already uses the 2s
   default handshake timer.
3. **Per-account `limits`** in `fleet-accounts.conf.tmpl`:
   - `SYS:            { max_connections: 4,   max_subscriptions: 16 }`
   - `STARSHIP_OPS:   { max_connections: 64,  max_subscriptions: 512 }`
   - `STARSHIP_EDGE:  { max_connections: 128, max_subscriptions: 512 }`
   - `STARSHIP_RANGE: { max_connections: 32,  max_subscriptions: 256 }`
   - `STARSHIP_TELEM: { max_connections: 32,  max_subscriptions: 16 }`
   These bound each role's blast radius below the server-wide 256 cap and pass
   through `gen-nats-accounts.sh` untouched (sed only substitutes placeholders).
4. **Tests** — `tests/test_nats_rate_limits.py`:
   - each `nats/*.conf`(+`.tmpl`) carries the hardened keys (`max_pending`,
     `max_subscriptions`, `max_closed_clients`, `max_control_line`,
     `write_deadline`, `ping_interval`, `ping_max`);
   - `fleet-accounts.conf.tmpl` has a `limits` block per account;
   - `max_pending >= max_payload` invariant holds in every config;
   - `nats-server -t` validates `fleet-bus.conf` and a generated
     `fleet-accounts.conf` (skips when nats-server is absent), and `-t` on
     `agent-bus.conf`.
5. **Nightly** — new Section 19 "NATS rate limits & connection caps
   (ASP-375/F-011)" in `scripts/check-nightly.sh`; add a
   `test_ci_assertions.py` entry asserting the section exists; update
   `docs/ops/NIGHTLY_PACKAGING_DEPLOY_CHECK.md` table/baseline.

- No nats-server version bump (2.14.x pinned in ISO/CI stays).
- Does not retitle the threat-model H-011 row (that H-011 is plaintext-creds,
  ASP-536); this ticket follows the F-011 hardening numbering used by
