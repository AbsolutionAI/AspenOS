# ASP-684 — H-024 P0-2: TLS by default in cell firstboot

**Source:** `docs/SECURITY_THREAT_MODEL_v2.2.md` §8 P2 item 16 (TLS by default).
**Blocks:** production cell commission checklist item 3, per H-024 IEC 62443-4-2 cell assessment.
**Issue:** ASP-684 · **Sweep:** ASP-701 (daily implementation sweep).

## Discovery — what actually exists today

The capability is **already built and shipped**, but unreachable by default. Three gaps:

1. **`scripts/gen-nats-tls.sh` (93 lines) exists** and generates a CA + server/client certs,
   `tls.conf.snippet`, and `client.env`. It is *never called* unless `STARSHIP_NATS_TLS=1`
   is set by hand in `/etc/starship/firstboot.env`. Nothing defaults it on.

2. **The TLS block in `starship-firstboot.sh` lives *inside* `_enable_accounts_bus`
   (lines 245–264) only.** Bus selection (lines 274–285) routes:
   | Profile | Bus | TLS block reachable? |
   |---|---|---|
   | `ops` | `_enable_accounts_bus` (generator present + `STARSHIP_NATS_MODE` default `accounts`) | yes |
   | `edge` | `_enable_agent_bus` | **no** |
   | `ops` without `gen-nats-accounts.sh` | `_enable_fleet_bus` | **no** |

   So `STARSHIP_NATS_TLS=1` set on an `edge` cell is silently ignored — the setting has no
   effect on the bus that cell actually uses. That is worse than "not the default": it is a
   documented knob that lies.

3. **`verify: false`** is hardcoded in the generated `tls.conf.snippet`. Server-authenticated
   TLS only. A client that steals a shared token still gets a valid channel if it can reach
   the port. H-024 requires mutual TLS for WAN deployment, and there is no way to ask for it.

## Decision — scope

Follow the exact shape of the three most recent controls in this repo (H-019 devonly,
F-013 digests, F-014 signatures): script change + gate script + fixture tests + CI job +
nightly section + threat-model disposition. Anything less is unenforced, which is how
H-020 rule 4 stayed unenforced for a release (see `docs/plans/ASP-672-package-classification-gate.md`).

## Design

### D1 — TLS mode resolution (fail-closed)

```
_resolve_tls_mode:
  STARSHIP_NATS_TLS explicitly 0/false/off  → off    (escape hatch, always wins)
  STARSHIP_NATS_TLS explicitly 1/true/on   → on
  profile ops or edge                       → on     (H-024 default)
  otherwise (server, dev)                  → off
```

Local single-node `server` profile stays plaintext: it is loopback-only agent-bus, and
forcing TLS there would break every dev box and CI fixture for no threat-model benefit.

### D2 — Fail closed, not fail silent

Today generation runs with `|| true`. If TLS is required by default, a generation failure
that silently leaves plaintext NATS running is **strictly worse** than no TLS default — it
manufactures a false sense of encryption. Therefore:

- TLS required + material absent after generation attempt → firstboot **exits non-zero**
  with an actionable message naming the log line and the opt-out.
- `STARSHIP_NATS_TLS_BEST_EFFORT=1` downgrades to a loud warning for commissioning
  windows where a cell must come up unencrypted to be reachable at all.

This is the one behavioural risk in the change and it is deliberate: a commissioning cell
that cannot do TLS fails the same way a cell missing `openssl` always should, loudly, at
first boot, instead of at 3am on the WAN.

### D3 — One TLS path for every bus mode

Extract the block into `_enable_nats_tls <active-conf>` and call it **after** bus selection
for all three modes. The active conf is resolved via `readlink -f /etc/starship/nats/active.conf`
so the function is bus-agnostic rather than duplicating itself three times.

### D4 — Mutual TLS as an opt-in flag

`gen-nats-tls.sh --mutual` emits `verify: true` (+ `verify_and_map: false`). Wired through
firstboot as `STARSHIP_NATS_TLS_MUTUAL=1`. Default stays `verify: false` — mTLS requires
every client to carry a cert and would break interop with existing edge agents that do not
yet ship one. WAN deployment docs name it as the requirement.

### D5 — Gate enforcement

`scripts/check-nats-tls-default.sh` asserts the structural contract (default resolution
present, all three bus paths reach TLS, mutual flag supported, fail-closed guard present,
no `verify: false` hardcode left behind) with a `--self-test` mutation mode, wired as CI job
`security-nats-tls` and nightly Section 23. Mirrors the H-019 gate's proven shape.
