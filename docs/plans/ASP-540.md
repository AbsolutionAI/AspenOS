# ASP-540: Gatekeeper shim — capability-based authorization (ADR-0009)

## Problem

ADR-0009 (H-008, H-009, H-020; threat model §4.1 / §8 P0#3) requires a local
gatekeeper that mediates agent access to real systems. Today
`src/python/gatekeeper/minimal_shim.py` **announces** `propose_act` + `requires:
dual_human` for safety-adjacent capabilities but never holds the proposal, never
collects human authorizations, and never refuses a bare forward. A single human
(or no human at all) can still forward any safety action — `propose_act`
self-authorization is not prevented.

## Success criteria (Phase 1 DoD)

1. **Intercept** — a local proxy intercepts `propose_act` on safety-adjacent
   subjects (`aspen.safety.*`, `aspen.edge.*.command`, `aspen.fleet.mission.start`)
   and never forwards until authorized.
2. **Dual-human** — two *distinct* human IDs collected via
   `aspen.authz.gate.decision` are required before forward. One human, a fresh
   proposal with no humans, or unknown/expired requests → `refuse`.
3. **Audit** — every propose / authorize / refuse / grant lands on the ASP-537
   `AuditEventPublisher` (JSONL always + `aspen.sentinel.audit.event` JetStream,
   `{event_id, actor, action, target, result, ts}` envelope).
4. **Subject contract** — agents talk to the gatekeeper only on
   `aspen.authz.gate.request` / `aspen.authz.gate.decision`; grants are emitted
   on `aspen.authz.capability.grant`. No broad credentials.

**Out of scope:** Hermes/Paperclip image credential strip, live Light Cell vs
Full Plant profile provisioning, Sentinel dashboard query UI, BEL-215 remainder.

## Solution

### 1. `src/python/gatekeeper/minimal_shim.py` — proposal + dual-human engine

- `SAFETY_SUBJECTS` becomes a real NATS-style matcher: new
  `is_safety_capability(capability)` uses `*`/`>` wildcards against the subject
  portion (action suffix stripped). Patterns: `aspen.safety.*`,
  `aspen.edge.*.command`, `aspen.fleet.mission.start`.
- New module-level proposal registry `PROPOSALS: dict[str, dict]` keyed by
  `request_id` with `{request_id, agent_id, capability, resource, profile,
  state (pending|granted|refused), humans[], created_at, updated_at,
  expires_at}`.
- Constants `DUAL_HUMAN_REQUIRED = 2`, `AUTH_WINDOW_SECONDS = 300` (mirrors
  ASP-538 `CLEAR_AUTH_WINDOW`).
- `request_capability(...)` safety path: **registers a pending proposal**, audits
  `propose_act.pending`, and returns a `propose_act` decision with
  `status=awaiting_authorization`, `humans_required=2`, `humans=[]`. **No token
  is minted.**
- New `authorize_gate_request(request_id, human_id, note=None)`:
  - unknown request / already refused → `refuse` (`unknown_request` / stays refused)
  - expired window → `refuse` (`authorization_window_expired`)
  - duplicate human → audits `gate.authorize.duplicate` and stays `awaiting`
    (H-009: distinct-principal enforcement rejects duplicates)
  - first/second distinct human → audit `gate.authorize` (with `auth_count`);
    at 2 distinct humans → `_grant_proposal` mints a short-lived scoped token,
    audits `capability.grant`, returns `decision=grant` + token + `humans`.
- New `forward_proposal(request_id)`: the forward gate.
  - granted → returns cached grant (idempotent)
  - pending with <2 humans → `refuse` (`insufficient_humans`), audits `gate.refuse`
  - expired → `refuse` (`authorization_window_expired`)
  This is the "bare forward / one human = refuse" contract.
- New async `_handle_gate_decision(data)` — inbound human authorization handler:
  extracts `request_id` + `human_id`, calls `authorize_gate_request`, returns the
  result dict (None when not a human authorization message).

### 2. `src/python/gatekeeper/nats_client.py` — decision subscription

- `__init__` gains `decision_handler` parameter.
- New `_subscribe_gate_decisions()` subscribes to `aspen.authz.gate.decision`
  and only invokes `decision_handler` when the message carries a singular
  `human_id` + `request_id` (so the gatekeeper's own publishes on the same
  subject are never mistaken for human approvals — no feedback loop).
- `_subscribe_gate_requests()` result path refactored into `_publish_result()`:
  publishes the outcome to `aspen.authz.gate.decision` (decision last) and, for
  grants, mirrors the token to `aspen.authz.capability.grant` via `publish_grant`.
- `run_daemon()` registers `_handle_gate_decision` as the decision handler.
- Multi-subscription lifecycle: `_subs` list, close() unsubscribes all.

### 3. Tests — `tests/test_gatekeeper_dual_human.py`

- safety classification matrix (`is_safety_capability`)
- proposal registration: safety request → `propose_act`, no token, state pending
- never-forward: 0 humans → `forward_proposal` refuses (`insufficient_humans`)
- single human → still `awaiting`; forward refuses
- distinct-principal: same human twice = 1; duplicate audited
- two distinct humans → `grant` + scoped token + `humans` on proposal
- refusal states: unknown request, already-refused stays refused, expired window
- audit: propose / authorize / duplicate / refuse / grant all land in
  `AUDIT_LOG` and in an `AuditEventPublisher` JSONL journal (ADR-0007 envelope)
- NATS wiring: `_handle_gate_decision` approves via mock subscriber; client
  with a decision handler subscribes to `aspen.authz.gate.decision`; a human
  approval on the mock queue drives a final `grant` → `aspen.authz.capability.grant`
  publish; non-human messages ignored
