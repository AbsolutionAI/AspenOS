# ASP-575: H-014 — Verify AppArmor profiles on all deployment targets

**Mode:** VERIFY-ONLY. No `aa-enforce`, no profile install, no CHG, no sudo
apply. This issue produces verification evidence, a plan, and compound notes —
not running-policy changes.

Threat model reference: `docs/SECURITY_THREAT_MODEL_v2.2.md` §8 P0#3 / H-014
(6.5, AV:L/AC:M).

## Problem

Profiles exist in `security/apparmor/` (`agnetic-agent`, `nats`, `ollama`) but
the threat model flags `scripts/install-daemon.sh` as possibly never installing
them. H-014 asks to verify profiles load on every deployment target and to fail
the build when a profile is present in source but absent from the installed
target. H-010 (capability-token lifecycle, closed in ASP-564) is the adjacent
risk: without AppArmor confinement, a compromised agent process can `ptrace`
peers or read `/proc` to exfiltrate gatekeeper tokens / NATS credentials, so the
AppArmor layer is the residual host-side control that makes token handling
meaningful.

## Scope

- Inventory source profiles vs this host's loaded/absent profile set.
- Trace **every** deployment target to confirm whether profiles are installed
  and whether anything validates load at install or in CI.
- Produce a verification report, a remediation plan, and compound notes.
- Do **not** change running security policy on any host.

## Deployment targets (the places profiles must reach)

| Target | Artifact | AppArmor wiring today |
|--------|----------|------------------------|
| Manual daemon install | `scripts/install-daemon.sh` | **None** — no `install-apparmor.sh` call, no profile copy |
| Debian package | `scripts/build-deb.sh` → `debian/DEBIAN/{postinst,prerm,postrm}` | **None** — profiles not staged into `.deb`; no `postinst` hook |
| ISO image (edge/server/ops) | `iso/config/hooks/0100-agnetic-install.chroot` + `iso/autoinstall/user-data.*.yaml` | **None** — hook installs Ollama/NATS/create users, never AppArmor |
| CI / nightly gate | `.github/workflows/ci.yml`, `nightly.yml`, `scripts/check-nightly.sh` | **None** — no AppArmor section, no load verification, no fail-if-missing |

`scripts/install-apparmor.sh` exists and is correct (copies to `/etc/apparmor.d`,
`apparmor_parser -r`, `aa-enforce`) but nothing calls it. It is documented only
as a manual step in `SECURITY.md` (root `SECURITY.md:45`) and
`docs/SECURITY.md:81`.

## Verification results (summary)

Full detail in `docs/asp-575-apparmor-verification-report.md` (uploaded to this
issue as an attachment). Headline:

- **Source:** 3 profiles present in `security/apparmor/`; installer script
  present.
- **Host (this sandbox):** AppArmor kernel active, 309 system profiles loaded;
  `agnetic-agent` / `nats` / `ollama` profiles **absent**. `ollama` is installed
  and **running unconfined** (`/usr/local/bin/ollama serve`, pid found at
  verify time). Host is a dev workstation — no `/opt/agnetic|/opt/starship`, so
  not itself a Starship deployment target.
- **All 4 deployment targets fail to install or verify profiles** — H-014
  gap CONFIRMED exactly as the threat model suspected.
- **Path drift:** `ollama` profile attaches `/usr/bin/ollama` but the ISO hook
  and this host install to `/usr/local/bin/ollama` (profile would not attach).
  `agnetic-agent` uses legacy `/opt/agnetic` + `/etc/agnetic` (resolve via
  symlinks to `/opt/starship`+`/etc/starship`, but `docs/SECURITY.md:89`
  already flags updating to 2.1 paths). `nats` profile attaches
  `/usr/local/bin/nats-server` — matches the ISO hook install path.

## Remediation plan (follow-up, NOT this issue)

For a subsequent implementation issue, in order:

1. **Wire installer into every target:**
   - `install-daemon.sh`: invoke `install-apparmor.sh` (root path) after
     services are laid down.
   - `build-deb.sh`: stage profiles to `etc/apparmor.d/` in the package root;
     call `apparmor_parser -r` + `aa-enforce` (best-effort) from `postinst`.
   - ISO chroot hook: `apt-get install -y apparmor apparmor-utils`, copy the 3
     profiles, load with `apparmor_parser`, set enforce.
2. **Fix path drift:** update `ollama` profile to `/usr/local/bin/ollama`
   (and/or canonical install path). Normalize agent profile to
   `/opt/starship/bin/*` + `/etc/starship/**` with legacy symlink allowances.
3. **Add verification gate:**
   - New `scripts/check-apparmor.sh`: `aa-status` must show `agnetic-agent`,
     `nats`, `ollama` loaded; fail if profile exists in `security/apparmor/`
     but is absent on the target.
   - Wire into `scripts/check-nightly.sh` (new Section) and a small CI step.
   - `check-nightly.sh` "fail build if missing" semantics per §8 P0#3.
4. **Update threat model:** flip H-014 status to reflect fixed gap after the
   implementation slice lands.
