## 2. Problem

ASP-379 shipped a **fail-open, log-only** behavioral anomaly detector
(`ToolAnomalyDetector`, R1–R4) over ADR-0007 tool-audit events, but nothing
consumes the live audit stream. The threat model
(`docs/SECURITY_THREAT_MODEL_v2.2.md` §8 P1 #14) tracks the residual wiring:

> Subscribe a JetStream consumer to the tool-audit subject, feed events through
> `ToolAnomalyDetector.feed()`, publish findings to a `sentinel.tools.anomaly`
> subject so ops can page on R1 (high) and template on R2–R4.

## 3. Design decisions

| Decision | Why |
|----------|-----|
| New module `src/python/sentinel/tool_anomaly_consumer.py` | Sits beside the detector + audit publisher/consumer it composes; mirrors the `sentinel.*` module layout |
| Subject `aspen.sentinel.tools.anomaly` (env `ASPEN_TOOLS_ANOMALY_SUBJECT`) | The threat model's `sentinel.tools.anomaly` is the short form; the durable `ASPEN_SENTINEL` stream binds `aspen.sentinel.>` (audit + fleet overview already live there), so the finding subject must be namespaced under it to be captured |
| **Local-first write topology** (JSONL always + JetStream best-effort) | Same contract as `sentinel.audit` / `sentinel.fleet_overview`: findings are durable offline; a missing broker never drops a finding |
| Reuse `ToolAnomalyDetector` unchanged | The detector is already tested (12 tests); wiring must not change detection semantics |
| Publish `Finding.to_dict()` + `finding_id`/`ts`/`source`/`notify` envelope, `Nats-Msg-Id = finding_id` | Idempotent replay; ops can page on `notify: true` (severity == page severity, default `high`) and template the rest |
| **Fail-open end to end** | Detector never raises; a bad message or publish failure is logged and swallowed — never blocks `propose_act` |
| Findings journal `ASPEN_ANOMALY_LOG` → `/var/lib/aspen/sentinel/tool-anomaly.jsonl` | Matches sibling journals; offline inspectable |
| Live subscribe via core `nc.subscribe` (no durable name), matching `sentinel.consumer` | The detector holds an in-memory sliding window; replaying a durable backlog into a fresh process would re-window stale events as if live. The audit journal is the durable source (replayable via `ingest_journal`). Prevents double-consumption surprises |
| No systemd unit in this change | Wiring is the deliverable; service enablement is deployment scope and would need ops review (follow-up) |
