# ASP-678: Paperclip advertises an unreachable API base to every agent run

**Status:** Discovery complete. Plan only — no fix applied. The remedy is a host/bind change and
belongs to Aspen Architect / Captain under the CHG rule, not to implementation.

## Problem

Every agent run in this company is injected `PAPERCLIP_API_URL=http://10.242.32.120:3100`.
The Paperclip server does not listen on that address. The documented way for an agent to talk to
the control plane is `curl` against `$PAPERCLIP_API_URL`, so that instruction fails for every
agent, every run, with `connection refused`.

The failure is silent from the board's point of view: the agent run is lost, the issue keeps its
old status, and a later wake retries it. The observable symptom is a growing pile of
`process_lost_retry` wakes and recurring issues that never reach a disposition.

This has been open since at least 2026-09-09 and was recorded inline in run results instead of
being fixed:

| Doc | Recorded |
|---|---|
| `docs/sweep-results-2026-09-09.md:54` | `Paperclip API unreachable (10.242.32.120:3100 connection refused)` |
| `docs/sweep-results-2026-09-11.md:47` | same |
| `docs/ops/nightly-results-2026-09-15T08-15.md:47` | same |
| `docs/ops/nightly-results-2026-09-15T08-16.md:44` | same, plus `127.0.0.1:3100` |

Four independent runs worked around it by writing results to local files and commits. No issue was
ever filed. A sweep of all 473 company issues found none for this defect.

## Evidence (2026-09-28, this run)

The server binds the tailnet address only. `ss` shows one listener, and it is not the advertised one:

```
$ ss -ltnp | grep 3100
LISTEN 0 511 100.78.55.13:3100 0.0.0.0:* users:(("node",pid=15892,fd=49))
```

`/home/tech/.paperclip/instances/default/config.json`:

```
server.bind            = tailnet
server.host            = 0.0.0.0
server.port            = 3100
allowedHostnames[0]    = 10.242.32.120
allowedHostnames[2]    = 100.78.55.13   <- the address actually bound
```

Startup banner agrees — `Bind tailnet (100.78.55.13)`, `Server 3100`,
`API http://100.78.55.13:3100/api`.

The advertised base is the only thing that fails:

```
$ curl -sS -m 10 http://10.242.32.120:3100/api/health
curl: (7) connect to 10.242.32.120 port 3100: Connection refused

$ curl -sS -m 10 http://100.78.55.13:3100/api/health
{"status":"ok","deploymentMode":"authenticated",...}          # HTTP 200
```

`10.242.32.120` is a real local address (`enp10s2`), so the failure is "nothing is listening
here", not "no route to host". The control plane is healthy; only the advertised base is wrong.

## Root cause

`server.bind = "tailnet"` (a `--bind` quickstart preset, CHG-0021) resolves the bind address to
the `tailscale0` v4. The value injected into agent runs is a different address on the same host,
and it matches `allowedHostnames[0]`, not the bound address.

Working hypothesis: the runtime advertises `allowedHostnames[0]` as the API base rather than the
address it actually bound. The correlation is exact — advertised base equals `allowedHostnames[0]`
in both the env var and the agent prompt, and the real bind address sits at index 2. This is
inferred, not proven: pinning it down needs either a source read of the URL-derivation path in
`~/.local/lib/node_modules/paperclipai` or a controlled config change, neither of which
implementation should do unasked.

The config is coherent on its own terms — `10.242.32.120` is in `allowedHostnames` and passes the
host check. It only becomes a bug because the advertised URL is chosen independently of the bind
address. That is the defect to fix: **advertised base and bound address must be derived from the
same source.**

## Success criteria

- `curl -sS "$PAPERCLIP_API_URL/api/health"` returns HTTP 200 from inside an agent run, with no
  per-agent override.
- The advertised base equals the address the server binds, for every `server.bind` mode
  (`loopback`, `lan`, `tailnet`).
- A run whose process is lost resumes and reaches a disposition instead of retrying blind.
- `docs/sweep-results-*.md` and `docs/ops/nightly-results-*.md` stop carrying the
  "Paperclip API unreachable" note.

## Options for Aspen Architect / Captain

**1. Derive the advertised base from the resolved bind address (recommended).**
Fixes the class of bug, not the instance. If it is a one-line change in the paperclipai runtime,
prefer it; if it needs an upstream release, the config workaround below is the interim.

**2. Interim config workaround — reorder `allowedHostnames`.**
If the runtime advertises `allowedHostnames[0]`, moving `100.78.55.13` to the front makes the
injected base correct without touching code. Cheap and reversible, and it makes hypothesis above
decisive on the next run: if the injected base changes with no other edit, the hypothesis is
confirmed.

```
allowedHostnames: ['100.78.55.13', '10.242.32.120', '10.242.32.145', 'bt-asp-srv', ...]
```

**3. Do not set `server.bind = "lan"`.**
The LAN IP is what is already advertised, so this looks like the shortest fix. It is wrong:
CHG-0021 moved the bind to `tailnet` deliberately, because binding `3100` before `tailscale0`
had its v4 crashed the unit with `EADDRNOTAVAIL`. Reverting trades a misadvertised URL for the
crash loop that CHG-0021 was written to stop.

## Not in scope

- Changing `server.bind` or any host, Tailscale, or nginx setting. CHG rule: host/bind changes go
  through `/home/tech/.aspen/ops` and are never silent. Implementation does not hold this lever.
- Restarting the Paperclip control plane to test a config change. It is currently hosting live
  runs for aspen, Auditor, and packndeploy; a restart mid-heartbeat would kill them.
- Per-agent `API=http://100.78.55.13:3100` overrides in individual agent scripts. That reproduces
  the workaround already in the run logs and hides the defect; it is a diagnostic step, not a fix.

## Interim guidance for agents

Until this is fixed, an agent that needs the control plane should use the tailnet base and keep
using it for every call in the run, not just the first:

```bash
API="http://100.78.55.13:3100/api"   # server.bind=tailnet; $PAPERCLIP_API_URL is wrong
curl -sS -H "Authorization: Bearer $PAPERCLIP_API_KEY" "$API/..."
```

This is what unblocked the ASP-678 sweep, which is how the defect was found.
