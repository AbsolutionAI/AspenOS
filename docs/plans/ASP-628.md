# ASP-628: Gatekeeper production packaging placement (ADR-0009 residual)

**Parent:** ASP-627 Weekly Architecture Review (2026-09-21)  
**ADRs:** ADR-0009 (Accepted P1+P2) · ADR-0004 · ADR-0008  
**Linear:** BEL-215 residual (packaging only — design locked)  
**Status:** Decision recorded 2026-09-21 · **no production image change this ticket**

## Problem

`src/python/gatekeeper/` is the monorepo ADR-0009 shim (Phase 1 dual-human +
Phase 2 token lifecycle / credential-strip proxy / safety enforcer). PACKAGES.md
still lists it as **Dev-only** prototype. Production packaging must choose one of:

1. **Edge-adjacent plugin** — optional per plant profile  
2. **Core-edge binary** — always-on on every AspenOS / Sentinel install  

Durable token backend (in-memory → Redis/PG) is **later** and not part of this
DoD under freeze.

## Decision

**Placement: Edge-adjacent Plugin.**

| Field | Value |
|-------|--------|
| Package name | `aspen-gatekeeper` |
| Classification | **plugin** (ADR-0008) |
| Install surface | Plant / edge profiles that run safety-adjacent agents or OT drivers |
| Not installed by default on | C2-only / Sentinel-dashboard-only / pure-dev nodes |
| Source (today) | `src/python/gatekeeper/` (monorepo SoR until mesh extract) |
| Production images (this ticket) | **unchanged** — captain required before deb/ISO/systemd unit |

### Why not core-edge always-on

1. **ADR-0004** keeps the kernel thin: “Policy + governance gates” stay as
   *contracts* in core (`aspen-safety` — estop + propose_act enforcement policy).
   The full dual-human daemon, token registry, and NATS gate client are a larger
   surface than every install needs.
2. **Weekly reviews already pointed edge-adjacent:**
   - 2026-08-24: G8 gate library lives in **edge-rrm**, not monorepo kernel /
     Paperclip; monorepo scripts were proof harnesses.
   - 2026-08-31 / 2026-09-07: prefer **edge-adjacent plugin**, not Paperclip;
     monorepo path remains prototype until packaging chooses.
3. **ADR-0009 modular profiles** (Light Cell vs Full Plant) modulate *capability
   manifests*, not “every node runs a gate daemon.” Optional plugin + profile
   manifests match that model.
4. **Attack surface:** always-on gatekeeper on C2-only images expands NATS authz
   surface and H-020 SPOF footprint without OT benefit. Plugin-on-edge keeps the
   safety path next to RRM/drivers where `propose_act` actually matters.
5. **Core already names safety policy:** PACKAGES.md Core lists `aspen-safety`
   (estop, propose_act enforcement). That core row stays; it is **not** the same
   package as the gatekeeper service.

### Split of responsibility

```
aspen-safety (Core)              aspen-gatekeeper (Plugin)
─────────────────────            ──────────────────────────
estop precedence                 dual-human propose_act hold
propose_act *policy* contracts   token issue/consume/refresh/expire
fail-closed subject rules        GatekeeperProxy / NATSAgentProxy
(always present)                 SafetySubjectEnforcer (runtime gate)
                                 NATS daemon on aspen.authz.*
                                 (optional per plant/edge profile)
```

EdgeRRM / `aspen_edge.gate` remains the fleet product path for G8; monorepo
`aspen-gatekeeper` is the capability-token + dual-human + credential-strip
implementation that plant/edge installs compose beside it. **Not** inside
Paperclip / aspen-dev images.
