# ASP-432: HITL vault approval gate for physical cell act (H-022, G9 prerequisite)

**Source:** ASP-432 (H-022) — physical G9 path blocked on vault/H-022 (Weekly Review 2026-09-21 §96)
**ADR reference:** ADR-0003 (fleet/edge safety contracts) · ADR-0007 (authz gate.decision) · ADR-0009 (capability-based gatekeepers) · ADR-0012 (operator-of-record binding)
**Related:** ASP-540/ASP-564 (gatekeeper phases) · ASP-628 (gatekeeper packaging) · ASP-370 (host baseline soft gate) · ASP-433/435 (H-023/H-025 siblings)

## Problem

The gatekeeper (`src/python/gatekeeper/minimal_shim.py`) treats all safety-adjacent `propose_act` the same way: register an **in-memory** `PROPOSALS` entry, hold for two distinct human authorizations on `aspen.authz.gate.decision`, then grant a short-lived capability token. For a physical cell act (H-022) that in-memory record is not a durable, auditable, human-reviewable artifact — it evaporates on process restart, cannot be inspected by a human operator over time, and is not an operator-of-record in the sense ADR-0012 §2 requires before non-sim arm.

G9 (non-sim arm) needs a **durable vault approval record** that:

1. Is created at request time alongside the proposal,
2. Survives gatekeeper restart,
3. Is human-reviewable as an Obsidian/Markdown note,
4. Is consulted before the capability is granted,
5. Fails **closed** (no grant) if the vault record is missing/unapproved.

The repo already has the persistence layer: `services/hitl.py` (`HITLManager` SQLite approvals) and `services/hitl_vault.py` (`HITLVault` Obsidian note bridge). ASP-432 wires them into the gatekeeper decision path for physical cell acts.

## Success Criteria

1. `is_physical_cell_act(capability)` classifier exists and is unit-tested (distinct from `is_safety_capability`).
2. On `request_capability()` for a physical cell act: dual-human proposal is registered **and** a durable HITL vault approval record is created in one call.
3. On `authorize_gate_request()` reaching dual-human threshold: grant is **refused** (`vault_approval_required`) unless the corresponding vault record exists and status is `approved`.
4. Vault/DB paths overridable via existing `HITL_DB` / `HITL_VAULT_DIR` env vars (`services/hitl_vault.py:26-27`) so tests are hermetic.
5. Test file `tests/test_gatekeeper_vault_gate.py` covers: physical vs non-physical classification, vault record created on request, grant without vault → refuse, grant with approved vault → grant, duplicate-human still ignored, unknown_request refuse, restart-persistence via re-read from SQLite.
6. All existing gatekeeper tests continue to pass (13 + 77 + 21 + 22 + new; 0 failures).
7. No real hardware touched; `ASPEN_SIM=1` not required; Captain constraints honored (git-only, propose_act-only, plant-range).

## Design

### 1. Capability classifier

Add to `minimal_shim.py`:

- `PHYSICAL_ACT_SUBJECTS` — the subject patterns that designate a physical cell act, e.g. `aspen.edge.*.act`, `aspen.safety.*.act`, `aspen.edge.*.command` (align with ADR-0003 propose_act subjects). Excluded: `light-cell` profile requests (those stay on the plain dual-human path).
- `is_physical_cell_act(capability, profile, patterns=None)` — applies `_subject_match` (existing, `minimal_shim.py:183`) to the capability subject; returns True only for physical-act patterns on non-sim profiles.

### 2. Vault record creation on request

At `request_capability()` (`minimal_shim.py:732`), interleave into the safety branch (step 2, currently at `minimal_shim.py:808`):

```python
if is_safety_capability(capability):
    proposal = _register_proposal(agent_id, capability, resource, profile, request_id)
    vault = _ensure_vault_approval(proposal, profile)   # new
    ...
```

`_ensure_vault_approval` (new module `src/python/gatekeeper/vault_gate.py`):

- Uses `services.hitl.py` `HITLManager.create_request(tool, arguments, agent, context)` to insert a durable SQLite approval row (tool = capability or `propose_act`, arguments = `{resource}`, agent, context = `{request_id, profile, physical: True}`).
- Uses `services.hitl_vault.py` `HITLVault` to materialise the Obsidian note (`sync()` writes `{req_id}.md` from the DB; `create()` is a direct fallback when DB is pre-populated).
- Returns `{hitl_request_id, note_id, status: "pending"}`; stores the map `request_id → hitl_request_id` in module state AND in the proposal dict so the gate can re-check on grant.
- **Fail-closed:** if the vault layer raises (DB unwritable, note write fails), the capability path returns `deny` with reason `vault_unavailable` — never a silent grant.

### 3. Vault check before grant

In `authorize_gate_request()` at the dual-human threshold (`minimal_shim.py:701`):

```python
if len(proposal["humans"]) >= DUAL_HUMAN_REQUIRED:
    if is_physical_cell_act(proposal["capability"], proposal["profile"]):
        return _vault_gate(proposal)   # refuse vault_approval_required unless approved
    return _grant_proposal(proposal)
```

`_vault_gate` re-reads the HITL row / vault note (by stored `hitl_request_id`), accepts only status `approved` (via `HITLManager.get_request` / `HITLVault.get`), else returns:

```json
{ "decision": "refuse", "reason": "vault_approval_required",
  "request_id": "...", "humans": [...], "humans_required": 2 }
```

New refuse reason joins the stable set (ADR-0012 table): `unknown_request`, `insufficient_principals`, `duplicate_principal`, `self_approval` (already `unknown_request`/`duplicate` in this shim), plus **`vault_approval_required`**.

### 4. Wiring & config

- `src/python/gatekeeper/vault_gate.py` owns all HITL imports so `minimal_shim.py` gets no new hard dependency (mirrors existing late-import style used for NATS/sentinel).
- Paths resolved from `HITL_DB` / `HITL_VAULT_DIR` env at call time (env-overridable for hermetic tests, matching `hitl_vault.py`).
- No change to `gatekeeper_proxy.py` or `safety_enforcer.py` wire shape; decision dict gains a `vault_approval_id` field only for physical acts.

### 5. Audit events

- `gate.vault_created` — on request (request_id, hitl_request_id, capability, profile).
- `gate.vault_refuse` — on refused grant (request_id, reason vault_approval_required).
- `gate.vault_unavailable` — on fail-closed deny.

### Non-goals

- No operator registry / auth binding UI (ADR-0012 implementation follow-ups).
- No change to DualHumanGate in `aspen-edge-rrm` (external repo; RRM consumes the granted token).
- No estop dual-clear path (separate, ASP-538 pattern).
- No physical motion, no ASP-418 hardware scope.

## Out of Scope

- ASP-433 (estop watchdog), ASP-435 (OT segmentation) — sibling H-0xx.
- ADR-0012 acceptance + binding proof (G9 row; separate ticket).
- Gatekeeper packaging changes (ASP-628 governs module surface).

## Implementation Note (OpenCode, 2026-09-23)

Landed as `src/python/gatekeeper/vault_gate.py` + wiring in `minimal_shim.py` +
`tests/test_gatekeeper_vault_gate.py`. Two deviations from the design above,
both forced by repo reality:

1. **`services.hitl` / `services.hitl_vault` are not importable as `services.*`
   from the gatekeeper.** `src/python/services` (a regular package without
   `hitl.py`) shadows the root `services/` namespace whenever `src/python` is on
   `sys.path`, which is always true for the gatekeeper and its tests.
   `vault_gate.py` therefore loads the root `services/hitl.py` and
   `services/hitl_vault.py` module files by explicit path under private
   sys.modules names. The single HITL implementation stays authoritative.
2. **HITLManager's DB path is module-level, not env-driven** (`services/hitl.py`
   DB_PATH), while HITLVault already honors `HITL_DB`. `vault_gate` re-points
   the shared HITLManager store at `HITL_DB` when that env is set, so one knob
   (`HITL_DB`) keeps create-request and note-sync on the same hermetic file.
   Defaults (env unset) are untouched.
3. **Fixed a latent `services/hitl_vault.py` bug**: `sqlite3.Row` has no
   `.get()`, so `HITLVault.sync()` always raised on the first real row and never
   materialised notes. Replaced with key access + `or ""`.

Additionally, `aspen.edge.*.act` was added to `SAFETY_SUBJECTS`: without it, a
physical act subject would not have been intercepted by the dual-human proposal
path at all (it is the most safety-critical subject type). `aspen.safety.*` is
intentionally NOT a physical-act pattern — `aspen.safety.estop` must keep the
fast plain dual-human path (existing tests + operator safety), and a physical
estop act is covered by `aspen.safety.*.act`.

Verification: full test suite `448 passed, 4 skipped` (includes the 15 new
vault-gate tests); no real hardware; `ASPEN_SIM` never required.
