# ASP-659: Nightly check concurrency guard

**Source:** ASP-659 (child of ASP-657 daily implementation sweep) · runbook `docs/ops/NIGHTLY_PACKAGING_DEPLOY_CHECK.md`
**Related:** ASP-656 (nightly packaging & deployment check, owned by packndeploy) · ASP-658 (repo hygiene follow-up, packndeploy)

## Problem

`scripts/check-nightly.sh` has no concurrency guard, and its checks mutate shared state **in the working tree**. Two overlapping runs therefore corrupt each other and report the other's breakage as check failures.

Observed 2026-09-26 (evidence captured on ASP-659):

| Run | Result | Failures |
|---|---|---|
| packndeploy, ASP-656 run `863a67cf` | 149 pass / 1 fail | C11 p50 (known deviation) |
| this sweep, run `6ff287a4` | 148 pass / 2 fail | C11 p50 (known) + `sandbox_native import`; plus `deb package builds` |

Both extra failures pass in isolation with no concurrent run:

- `PYTHONPATH=agents python3 -c "from sandbox_native import sandbox_binary, native_enabled; assert sandbox_binary()"` → `ASSERT OK`
- `bash scripts/build-deb.sh` → `starship-os_2.2.0_amd64.deb`, 6.4M, 130 files

### Root cause

1. `scripts/build-deb.sh:56` runs `rm -rf "$PKG_ROOT"` then re-stages. A parallel run deletes the staging tree mid-build, producing `missing required path in package: DEBIAN/control`.
2. Section 3 relinks C11 binaries under `src/c/*/` via `make -C src/c/sandbox_spike`. A parallel relink transiently removes `sandbox_run`, so `sandbox_native import` asserts false.
3. `check()` funnels every check's stdout/stderr to a fixed `/tmp/nightly-check.log`, so a parallel run can splice the other run's output into a failure diagnostic — making a transient fault look like a specific, confident regression.

This is worse than wasted cycles: a nightly engineer receiving "2 new regressions" at 02:00 will reasonably open two investigation tickets against code that is fine. The baseline deviation count is the signal this check exists to protect, and concurrency corrupts it.

## Success criteria

1. Exactly one `check-nightly.sh` run executes the suite per checkout at a time.
2. A contending invocation fails fast with an unambiguous message and exit code `75` (`EX_TEMPFAIL`), so a scheduler retries instead of recording a phantom regression.
3. An isolated run still reports 149 pass / 1 known fail (C11 p50) — no deviation from the baseline table.
4. The runbook documents the guard and the reserved exit code.

## Design

Add an exclusive `flock(1)` on a run-scoped lock file, taken immediately after `cd "$REPO_DIR"` and held on a dedicated file descriptor for the process lifetime.

```
LOCK_FILE="/tmp/starship-nightly.lock"
exec 9>"$LOCK_FILE"
if ! flock -n 9; then
  echo "another nightly check already holds $LOCK_FILE — refusing to run concurrently" >&2
  exit 75
fi
```

### Why a fixed `/tmp` path rather than `${TMPDIR:-/tmp}`

An earlier draft of this plan scoped the lock to `TMPDIR`. That is wrong for this fleet: every
agent run is injected with its **own** `TMPDIR` (Paperclip gives each heartbeat a private
`/tmp/paperclip-run-*` directory), so a `TMPDIR`-scoped lock would give every run a private lock
and guard nothing. A fixed `/tmp` path is what makes the guard global across the concurrent
agents it exists to serialize. It also matches the fixed `/tmp/nightly-check.log` the `check()`
helper already assumes.

### Why `flock` and not a `mkdir` lockfile

`flock` is an advisory kernel lock tied to the open file description. It is released automatically when the holding process exits for any reason, including `SIGKILL`. A `mkdir`-based lockfile leaks on a killed run and needs stale-lock reaping, which is exactly the failure mode that would block the nightly unattended. `flock(1)` ships in util-linux and is present on `ubuntu-latest` runners, so CI needs no dependency change.

Inheriting fd 9 into child processes is deliberate, not incidental: the build children spawned by
`make` / `build-deb.sh` are still mutating shared in-tree state, so the lock must outlive a parent
that is killed mid-run. The lock is released when the last process holding it exits.

### Why exit 75

`75` is `EX_TEMPFAIL` and is reserved here, distinct from the script's `exit "$FAIL"` convention where the code is the number of failed checks. On contention the run must not be silently skipped — no verification happened — and it must not be reported as a code regression. A reserved non-zero code plus a loud stderr line gives a scheduler a retry signal and gives a human an unambiguous explanation.

Residual ambiguity (75 could in principle also mean 75 failed checks) is accepted: the suite has 150 checks, a 75-failure run would already be reported as `NIGHTLY CHECK FAILED (75 failures)`, and the contention message is written to stderr before that summary is ever reached. Documenting the reservation in the runbook closes the loop for readers.

### Scope boundaries

- Per-check log paths are **not** changed. Once runs are serialized there is a single writer, which is what the fixed `/tmp/nightly-check.log` already assumed.
- Build-artifact isolation via per-run worktrees is **out of scope**. It is the architecturally heavier answer; if lock contention recurs despite the guard, raise it with the Aspen Architect.
- The `exit "$FAIL"` convention for genuine check failures is unchanged.

## Tests

1. **Contention** — hold the lock in one shell, invoke `check-nightly.sh` in another, assert exit 75 and the contention message.
2. **Release** — after the holder exits, a new invocation proceeds past the guard (no stale lock).
3. **Regression** — an isolated full run reproduces baseline 149 pass / 1 known fail, with the C11 p50 deviation unchanged.
4. **Shell syntax** — `bash -n scripts/check-nightly.sh`, already covered by nightly section 7.
5. **End-to-end** — launch a real `check-nightly.sh` run, then a second invocation 3s later; the second must exit 75 with the contention message while the first is still progressing through the suite.

## Risks

- A long-running suite blocks a second manual run for ~70s. Acceptable: fail-fast is louder and more debuggable than queueing, and the operator can retry.
- Advisory locking is ignored by non-cooperating callers. Only `check-nightly.sh` needs to cooperate, and it now does; `make smoke` invoked directly remains unguarded and is out of scope.
