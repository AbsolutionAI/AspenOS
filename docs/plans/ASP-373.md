# Plan: ASP-373 — H-009/F-009 Enforce mode 600 on NATS creds & secret paths in packaging

## Problem

Python/security threat model F-009 (carried from the ASP-298 refresh): deb
`postinst`, firstboot, and install/packaging scripts must `chmod 600` NATS
credentials and secret paths. Current tree (`1070598`):

- `scripts/starship-firstboot.sh` writes `/etc/starship/nats-token` and
  `/etc/starship/nats.env` as **640/644** (world/group readable perms on token).
- `debian/DEBIAN/postinst` creates the NATS dirs but does not lock secret paths
  to 600 on install/upgrade.
- `scripts/build-deb.sh` stages NATS config (incl. `server.conf`, which carries a
  static token) without enforcing 600 in the payload.
- `scripts/gen-nats-accounts.sh` already emits creds (`creds/*.env`, `*.nk`,
  `sys.env`, `nats.env`, `fleet-accounts.conf`) as 600/700 — good, keep.

## Approach

1. Add a small idempotent helper `scripts/fix-nats-secret-modes.sh [ROOT]` that
   locks (chmod 600) the NATS secret/config paths — `nats.env`, `nats-token`,
   `fleet-accounts.conf`, `fleet-bus.active.conf`, `server.conf`, everything
   under `creds/`, and TLS key material — and fixes ownership so the consumers
   that legitimately need read access (agnetic services for `nats.env`, nats
   daemon for the server confs) can still read at mode 600.
2. Call the helper from `postinst` (install/upgrade repair path) and
   `starship-firstboot.sh` (generation path); also correct the inline
   chmod/chown in firstboot so every write of `nats.env` / `nats-token` is 600.
3. In `scripts/build-deb.sh`, stage the helper and run it against `$PKG_ROOT`;
   add a post-build `dpkg-deb -c` check that fails if any NATS secret path in
   the payload is world/group readable.
4. Add `tests/test_nats_secret_modes.py`: runs the helper against a tmp fixture
   and asserts 600/700 modes; greps firstboot/postinst to prove they no longer
   use 640/644 on the secret paths.
5. Add `docs/solutions/asp-373-nats-secret-modes.md` compound note.
