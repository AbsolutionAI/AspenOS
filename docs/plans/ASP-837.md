## 2. Problem

ADR-0012 (Proposed) defines the operator-of-record binding model for DualHumanGate authorizations on non-sim plant profiles. The first implementation follow-up in the ADR (item #1) is:

> Operator registry schema in aspen-contracts + local JSON/SQLite enrollment CLI

Currently `human_id` values are free strings in sim profiles. For a non-sim arm, operators must be enrolled in a local registry before their `human_id` can be used as a bound principal. No enrollment mechanism exists.

## 3. Design decisions

| Decision | Why |
|----------|-----|
| **Monorepo interim SoR** — `src/python/services/operator_registry.py` | Follows the established pattern from ADR-0007 (FLEET.md was interim SoR for NATS subjects before aspen-contracts mirror). Schema and CLI live here; mirror to aspen-contracts is a later step. |
| **JSON-file backed** (`/var/lib/aspen/operator-registry.json`) | Matches the existing local-first pattern used by sentinel journals, gatekeeper audit, and service accounts. No SQLite dependency in this step — JSON is inspectable and sufficient for initial enrollment. |
| **CLI `scripts/operator-registry.py`** with subcommands `enroll`, `list`, `revoke`, `show` | Same pattern as `scripts/tool-anomaly.py`, `scripts/sentinel-audit.py`, etc. |
| **Schema** — each operator record has `human_id`, `display_name`, `enrolled_at`, `enrolled_by`, `aliases`, `status` | Covers ADR-0012 §4 (opaque stable string), §5 (bound session maps 1:1), and §7 alias-risk mitigation (registry enforces one human → one canonical `human_id`). |
| **No gatekeeper integration in this step** | Binding check in edge-rrm/gatekeeper is follow-up #2 — this step is the registry itself. |
| **No SQLite** | Simpler to start. SQLite upgrade can layer later without breaking the JSON schema. |
