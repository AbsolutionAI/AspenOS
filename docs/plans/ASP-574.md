# ASP-574: H-019 CI gate — Dev-only package isolation

## Problem

Threat model v2.2 §8 P0#2 / H-019 (6.0, AV:N/AC:H) and ADR-0008 define a
three-tier package classification (Core / Plugin / Dev-only) in
`docs/PACKAGES.md`. Dev-only tooling (`aspen-dev/` tree items: package-mesh
scripts, compound-engineering tools, grok-build sandbox, dev gatekeeper shim)
is **never** allowed in production Debian packages, ISO images, or Docker
artifacts. There is **no CI gate** enforcing this — a Dev-only path can leak
into a shipped image unnoticed (prior ticket ASP-567 was a false-done: the gate
script was never committed).

## Success criteria (DoD)

1. `scripts/check-no-devonly-in-prod.sh` exists and is executable.
2. It parses the classification from `docs/PACKAGES.md` (Dev-only tier), scans
   production paths (deb staging via `scripts/build-deb.sh`, ISO content via
   `scripts/build-iso.sh` / `iso/`, Dockerfile(s) when present), and **fails** if
   any Dev-only reference is found.
3. Wired into `.github/workflows/ci.yml` (new job or step) and
   `scripts/check-nightly.sh` (Section: production-hygiene).
4. Verified behavior: exit 0 on the current clean tree; exit 1 on a planted
   Dev-only path.
5. Compound note under `docs/solutions/`.

## Solution

### 1. `scripts/check-no-devonly-in-prod.sh`

A `bash` script, `set -euo pipefail`, mirroring the style of
`scripts/check-nightly.sh` / `build-deb.sh` (REPO_DIR resolution, colored
pass/fail output, exit 1 on failure).

Logic:

- **Parse classification** from `docs/PACKAGES.md`:
  - Extract the **Dev-only** tier name and its example tokens from the
    classification matrix table row (`Dev-only | ... | package-mesh scripts,
    compound-engineering tools, grok-build sandbox, gatekeeper-shim (dev)`).
  - Extract the explicit **Dev-only Examples** list under
    `## Dev-only Examples (internal only)` (`aspen-package-mesh`,
    `compound-engineering-gate-tools`, `gatekeeper/minimal_shim.py`).
  - Canonical marker for the ownership tree: `aspen-dev/` (ADR-0008 rule 3:
    "Dev-only confined to `aspen-dev/` repo").
  - Build a normalized grep pattern (case-insensitive) of Dev-only package /
    tool / path tokens, minus noise words like `scripts`/`tools`.
- **Scan production surfaces**:
  - `debian/` (deb control + install scripts), `iso/` (package lists, hooks,
    chroot includes), `packaging/`, plus any `Dockerfile` / `*.dockerfile` /
    `.dockerignore` anywhere under the repo root.
  - Files staged by `scripts/build-deb.sh` into the `.deb` (the copied source
    trees: `agents/`, `dashboard/`, `tray/`, `skills/`, `souls/`, `nats/`,
    `config/`, `systemd/`, `src/c/`) and `scripts/build-iso.sh` (same trees plus
    `scripts/`). Scan the source paths that feed the images rather than build
    artifacts (`dist/`, `*/target/` excluded).
  - Grep for the Dev-only pattern across those paths; skipping binary/build
    artifacts and `.git/`.
- **Report**: each match → `FAIL dev-only reference in <path>: <line>`; a
  summary line `Dev-only isolation gate: PASS` / `FAIL (N references)`; exit
  code 0 / 1.

### 2. `.github/workflows/ci.yml`

Add a `pkg-hygiene` job (or an explicit step in an existing job) that runs
`bash scripts/check-no-devonly-in-prod.sh` with no special deps (pure
bash/grep, no install needed). Fail the workflow on non-zero.

### 3. `scripts/check-nightly.sh`

Add a `── Section: Production hygiene ──` `check "dev-only isolation gate"
bash scripts/check-no-devonly-in-prod.sh` (fits the existing `check()`
helper).

### 4. Threat model tick

Mark `§8 P0#2` / H-019 line implemented once the compound note lands
(consistent with prior slices); the DoD does not require it but keeps the
tracking table accurate.

### 5. Compound note

`docs/solutions/asp-574-devonly-ci-gate.md` — walkthrough, marker extraction
method, test evidence, wiring pointers.

## Verification

- `bash scripts/check-no-devonly-in-prod.sh` → exit 0 on current tree
  (verified no Dev-only refs exist in the scanned production trees).
- Planted-fail test: `echo 'aspen-package-mesh' > some-staged-path` (e.g. a temp
  file under a scanned tree) → exit 1; then remove it. Prefer an explicit
  self-test flag `--self-test` that plants a temporary marker in a temp
  directory passed via `CHECK_DEVONLY_ROOT` and asserts a fail, so the "exit 1"
  proof is part of the script's own verification.
- `bash -n scripts/check-no-devonly-in-prod.sh` clean.
- `scripts/check-nightly.sh` still green (script wired as one `check`).

## Out of scope

- Reclassifying packages / editing PACKAGES.md tiers.
- Scanning compiled artifacts inside `agent/target/` / `dist/` checksums
  (build trees are regenerated; source-of-truth scan is the gate).
- Docker image build workflows (none exist in this repo today).
